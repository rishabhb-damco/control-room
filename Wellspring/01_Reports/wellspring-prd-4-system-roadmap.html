PRD Part 4 of 4 · Design system

Color, type, spacing, icons

Same visual language established across all four PRD documents — dark teal, warm gold, parchment neutrals — carried into the product itself so the tool Wellspring's team uses daily feels like one continuous brand, not a bolted-on vendor app.

Color system

ink #17302e
accent #b3903f
paper #f5f0e8
success #3f7a56
warning #b06a1f
danger #a1402f

Semantic color (success/warning/danger) is separate from the brand accent (gold) and is reserved exclusively for state — SLA breach, eligible/ineligible insurance, stage health. Gold marks emphasis and navigation state only, never status, so the two systems never collide on the same element.

Spacing & icons

4px base unit; component padding steps at 8/12/16/24/32px. Icon set: a single consistent line-icon family at 20px/16px sizes, never mixed with a second icon style — used sparingly (nav, KPI context, status) rather than as decoration.

Component library

Buttons — primary (solid ink), secondary (outline), danger (solid, reserved for destructive confirms). States: default, hover (8% darken), focus (2px accent outline, keyboard-visible), disabled (40% opacity, no pointer).

Inputs & dropdowns — consistent 1px border, 5px radius, label above (never placeholder-only, per accessibility rule below), inline validation message beneath in danger color.

Badges, pills & tags — badges = system state (read-only, semantic color). Pills/chips = user-manageable (removable, neutral color unless a tag is itself semantic e.g. "Urgent").

Tabs — underline style, active tab in ink with gold underline, never more than 6 tabs before collapsing into an overflow menu.

Loaders, empty states, error states — inline spinner for sub-second waits; skeleton blocks for list/table loads >300ms; empty states always include a next action ("No leads match these filters — Clear filters"), never a bare "No data."; error states name what failed and offer Retry, never a generic "Something went wrong."

Accessibility

All interactive elements reachable and operable by keyboard alone; visible focus ring on every focusable element, never outline:none without a replacement.
Color is never the only signal — every badge/status pairs a color with a label or icon (e.g. "Eligible" text, not just green).
Contrast ratio ≥ 4.5:1 for body text in both themes, verified against both the parchment-light and teal-dark palettes above.
Forms: every input has a real <label>, errors are announced via aria-live, required fields marked both visually and in markup.

Security & HIPAA considerations

AreaApproach
AuthenticationEmail + password (Argon2id hashing), MFA (TOTP) available Phase 2, SSO/SAML reserved for Phase 3
AuthorizationRole-based via roles.permissions, enforced at both API middleware and DB row-level-security layer — never UI-only
Audit logsImmutable, insert-only audit_log_entries (AR-054) for every field change; a separate access_log records who viewed a lead detail page, not just who edited it — required for HIPAA "minimum necessary" review
EncryptionTLS 1.2+ in transit everywhere; encryption at rest at the database/volume level; column-level encryption for guardian_phone and any free-text clinical note fields
Backup strategyNightly full backup + continuous WAL archiving for point-in-time recovery; 30-day retention; quarterly restore drill logged as a compliance artifact
Session managementShort-lived access token (15 min) + rotating refresh token (7 days); server-side revocation list for immediate logout-everywhere on password change or admin-forced deactivation
Access logsEvery lead-detail view logged with viewer, timestamp, and lead ID — queryable from Audit Logs, filtered by entity
Role securityLeast-privilege defaults on every new role; Provider role in particular is scoped to consultations they're assigned to, never the full lead list
HIPAA postureHosting provider must carry a signed BAA before any lead record with health-adjacent fields (DOB, clinical notes, guardian info) is stored; leads.client_ref keeps this system PHI-light by design (see Part 1); breach-notification runbook defined before go-live, not after

Performance

ConcernApproach
CachingRedis-backed cache for dashboard aggregates, invalidated precisely by AR-044 on the write that affects them — never a blanket TTL guess
PaginationCursor-based on all list endpoints (leads, activities, audit log) — stable under concurrent writes, unlike offset pagination
Lazy loadingKanban board fetches cards per-column on scroll; Analytics charts below the fold defer render until in viewport
Real-time updatesWebSocket/SSE channel per organization broadcasts stage changes and new leads so two coordinators viewing the same board never see stale cards
Background jobsSync jobs, notification dispatch, report generation/export, and digest emails all run off a queue, never inline on a user request
Queue systemRedis-backed queue with per-job retry (exponential backoff) and a dead-letter queue after 3 failures, feeding the same Sync Monitor alerting as AR-053
Search indexingPostgres full-text + trigram to start (adequate at Wellspring's current volume); abstracted behind a search-service interface so a move to a dedicated engine needs no caller changes
ScalabilityStateless app tier behind a load balancer for horizontal scaling; DB scales vertically first, then via read replicas for reporting traffic (see Part 3 §Future scalability)

Future AI features (Phase 3)

Architecture: an assistant that calls the same read-scoped Reporting/Dashboard API endpoints defined in Part 3 — never raw SQL — so it inherits the same role-based permission boundary a human user has. All AI output is logged like any other system action; nothing it produces writes back to a lead record without an explicit human confirm.

CapabilityHow it works
Summarize lead historyCondenses a lead's Activity Timeline into a 3–4 sentence brief on open
Identify bottlenecksScans stage-aging distribution for outliers vs. the org's own historical baseline
Predict conversion likelihoodLightweight scoring model on structured features only (source, insurance eligibility, response time, day-of-week) — explicitly not on free-text clinical content
Suggest next actionRecommends "call now" / "send eligibility reminder" / "escalate" based on stage + SLA state, surfaced as a suggestion chip, never an auto-executed action
Generate management insights / exec summariesNatural-language pass over the existing AR-048 weekly KPI snapshot — turns numbers into a short narrative, doesn't invent new numbers
Detect anomaliesStatistical control-chart logic (same pattern as AR-026) generalized across any tracked metric, flags 2+ standard-deviation moves
Forecast workloadTime-series projection of lead volume vs. provider capacity, feeding the Provider Dashboard
Natural-language Q&AConstrained query translator that maps a question to Reporting API parameters (dimensions/metrics/date range) rather than freeform database access — cannot return anything the asking user's role couldn't already see

Guardrail: because Wellspring is a mental-health practice, no AI feature reasons over or surfaces verbatim clinical free-text in a way visible beyond the existing permission boundary — summaries stay operational (stage, timing, source), not clinical.

  • Structured intake form, Lead Detail, Activity Timeline
  • Pipeline board (9 default stages) + Table View

  • Core automations: AR-001–002, 008–009, 014–020, 023, 036–040, 050–052, 054
  • Executive + Intake dashboards
  • Admin: users, roles (fixed 5), referral/insurance taxonomy

Phase 2

Operational depth

  • Calendar View, Duplicate Review Queue + Merge screen
  • Full task/reminder/escalation automation set
  • Referral, Provider, Insurance domain dashboards
  • Report Builder, saved/scheduled reports
  • Command palette, saved filters/Smart Views
  • Full conflict-resolution UI for sync
  • MFA, webhooks, API keys

Phase 3

Scale & intelligence

  • Custom pipeline stages, custom roles
  • Visual automation rule builder (no-deploy rule authoring)
  • AI assistant (all 8 capabilities above)
  • SSO/SAML, SMS notifications
  • Database cutover from Sheets (repository swap, see Part 3)
  • Cohort analysis, forecasting, goal tracking

Testing strategy

Unit — stage-transition rules, automation condition evaluation, duplicate-scoring logic, insurance-eligibility checks
Integration — every API endpoint against a seeded test database, including permission-denial cases per role
End-to-end — critical flows scripted (intake → contact → schedule → convert; duplicate merge; sync round-trip) against a staging environment
Sync contract tests — against a Sheets API sandbox, including simulated rate-limit responses and injected conflicts
Migration/backfill testing — full dry-run import of all 32 historical tabs into staging, row counts and KPI totals reconciled against the March 2026 benchmark reference
Load testing — concurrent pipeline-board updates and a simulated sync burst at 60 writes/min to confirm graceful queuing, not failure
UAT — Wellspring coordinators shadow-run the platform alongside the live sheet for two weeks before cutover; sign-off required from at least one Coordinator and one Manager

Acceptance criteria — major features

Lead creation

Given a Coordinator submits the intake form with all required fields

When they save

Then a Lead is created with an auto-generated permanent display_id, assigned round-robin, and the duplicate check has run before the record is shown as saved

Duplicate detection

Given a new lead's phone number exactly matches an existing active lead

When the record is saved

Then both records are flagged "Possible duplicate — 90%+" and appear in the Duplicate Review Queue within the same request cycle, not a delayed batch job

Two-way Google Sheets sync

Given a staff member edits a cell in the connected Google Sheet

When the next sync cycle runs (webhook-triggered or ≤5 min poll fallback)

Then the corresponding Lead updates in the CRM, and if the same field was independently changed in the CRM since the last sync, a sync_conflicts row is created instead of either value being silently overwritten

Insurance eligibility gate

Given a lead's Insurance Carrier field is set to a carrier on the "not accepted" list

When a Coordinator attempts to advance the stage past Contacted

Then the transition is blocked, a "Verify/discuss self-pay" task is created, and a Lost-reason: Insurance suggestion is surfaced

SLA escalation

Given a lead has had no activity logged for 24 hours since creation

When the 15-minute cron evaluates SLA conditions

Then the owner is notified in-app and by email, and an "Overdue: first contact" task is created; a further 24h with no activity escalates a copy to the owner's Manager

Reporting export

Given a Manager runs a saved report for a custom date range

When they choose Export → PDF

Then a PDF matching the on-screen report renders within 10 seconds for date ranges up to 1 year, generated as a background job if it exceeds that

Role-based access enforcement

Given a user with the Intake Coordinator role

When they call any Admin-scoped API endpoint directly (e.g. /settings/pipeline-stages)

Then the API returns 403 regardless of what the UI does or doesn't show — permission enforcement never relies on the UI hiding a button

Lead merge

Given two leads are confirmed duplicates and a Manager commits a merge

When the merge completes

Then the surviving record's display_id is unchanged, the losing record's ID permanently redirects to it, both Activity Timelines are concatenated in chronological order, and an AuditLogEntry records the merge with both original IDs
