Frontend Technical Specification · Part 1 of 2

Stack & rationale

The PRD, UX Spec, database, API, automation engine, and system architecture are final. This document and its companion (Part 2) translate that approved spec into an implementation-ready frontend architecture — no new product features, only the engineering decisions needed to build it.

Adopting anything else means re-deriving sorting/filtering/pagination logic that already exists and is maintained.

Zustand, not Redux/Jotai/plain Context: almost all meaningful data in this app is server state and belongs in React Query, not global client state. What's left — sidebar collapsed, command palette open, active Smart View, in-flight Kanban drag state — is small, UI-only, and doesn't need Redux's ceremony or Jotai's atom-per-value granularity. Zustand's selector-based subscriptions also avoid the re-render cost a single Context would cause on high-frequency updates like drag position. Full mapping in State Management.

Recharts, with one deliberate exception: Recharts covers the KPI trend lines, funnel, and donut charts across every dashboard cleanly, has first-class React ergonomics, and needs no separate design-token bridge. Its one weak spot is the stage-aging heat map on the Operations Dashboard (PRD Part 1) — Recharts has no native heatmap primitive and forcing one through its grid/scatter APIs produces worse output than a small hand-built SVG grid component. That single widget is custom (~80 lines, documented in Component Architecture); everything else stays on Recharts.

Structure · 02

State management

CategoryOwnerExamplesRule
Server stateReact QueryLeads, tasks, dashboards, reports, sync status, audit log, notifications — everything from PRD Part 3's APIIf it comes from an API, it lives in React Query. Never copy a query result into Zustand/Context "for convenience."
Global UI stateZustandSidebar collapsed, command palette open+query, active Smart View, in-progress Kanban drag, themeOnly for state 2+ unrelated components need, that isn't itself server data
Cross-cutting session dataContextCurrent user + role + permissions (hydrated once at session start)Read-heavy, rarely-changing — Context's re-render cost doesn't matter here, and it avoids importing a store for something this static
Filter / pagination / sortURL search paramsPipeline Table filters, Report Builder parameters, pagination cursorAnything a user should be able to bookmark, share, or hit "back" on belongs in the URL, not in Zustand
Form stateReact Hook Form (local)Intake form, Settings forms, Merge field selectionsNever mirrored into global state; submitted directly to a mutation
Ephemeral component stateuseState/useReducerDialog open/closed, hover states, accordion expandDefault choice — promote to Zustand only when a second, unrelated component needs it

Anti-pattern to block in review: fetching a lead in a page component and passing it down as props through 4 levels of children. Every component that needs lead data calls its own (cached) useLead(leadId) — React Query dedupes the network request automatically, so this costs nothing and prevents prop-drilling rot.

Integration · 01

API integration

One hook per endpoint, one service file per PRD Part 3 API group. Query keys follow a factory pattern (constants/queryKeys.ts) so invalidation is typo-proof: queryKeys.leads.detail(id), never a hand-typed string.

// constants/queryKeys.ts
export const queryKeys = {
  leads: {
    all: ['leads'] as const,
    list: (filters: LeadFilters) => ['leads', 'list', filters] as const,
    detail: (id: string) => ['leads', 'detail', id] as const,
    activities: (id: string) => ['leads', id, 'activities'] as const,
    duplicates: (id: string) => ['leads', id, 'duplicates'] as const,
  },
  tasks: { list: (f: TaskFilters) => ['tasks', f] as const },
  // … one namespace per PRD Part 3 API group
}

// features/leads/hooks/useUpdateLeadStage.ts
export function useUpdateLeadStage(leadId: string) {
  const qc = useQueryClient()
  return useMutation({
    mutationFn: (stageId: string) => leadsService.changeStage(leadId, stageId),
    onMutate: async (stageId) => {
      await qc.cancelQueries({ queryKey: queryKeys.leads.detail(leadId) })
      const prev = qc.getQueryData(queryKeys.leads.detail(leadId))
      qc.setQueryData(queryKeys.leads.detail(leadId), (old: Lead) => ({ ...old, stageId })) // optimistic
      return { prev }
    },
    onError: (_err, _vars, ctx) => qc.setQueryData(queryKeys.leads.detail(leadId), ctx?.prev), // rollback
    onSettled: () => qc.invalidateQueries({ queryKey: queryKeys.leads.detail(leadId) }),
  })
}

General rule: GET hooks retry (2× exponential backoff, capped 10s) since they're safe to repeat. Mutations retry 0× by default — a failed write surfaces immediately as a toast with a manual Retry action, so a duplicate side effect never fires silently. The three exceptions (Log Activity, Attachment upload, Auth refresh) retry once because they're idempotent by design (activity IDs are client-generated, refresh is safe to repeat until the token is confirmed dead).

Integration · 02

Authentication

1
Login

useLogin posts credentials; server sets an httpOnly, secure, SameSite=Strict refresh-token cookie and returns a short-lived access token in the response body

2
Access token held in memory

Stored in a module-level variable inside lib/authToken.ts — never localStorage/sessionStorage, which are readable by any injected script. Lost on hard refresh by design; recovered via step 3.

3
Session bootstrap on load

Root (app)/layout.tsx calls useSession (/auth/me) on mount; the httpOnly cookie authenticates this call even with no in-memory access token yet, returning a fresh one

4
Silent refresh on 401

A single fetch interceptor in services/apiClient.ts catches any 401, calls /auth/refresh once (a module-level promise lock prevents concurrent requests from each firing their own refresh — "single-flight"), replays the original request, and only force-logs-out if refresh itself fails

5
Protected pages

middleware.ts checks for the refresh-token cookie on every (app)/* request; missing/expired redirects to /login?next= before any page code runs

6
Permission guards & role-based rendering

A <Can action="reassign" subject="lead"> component wraps conditional UI, backed by the same permission matrix as PRD Part 1 — but this is UX only. Every mutation hook's underlying endpoint enforces the same rule server-side (PRD Part 4's acceptance criteria: a hidden button is not a security boundary).

// components/shared/Can.tsx
export function Can({ action, subject, children, fallback = null }: CanProps) {
  const { role } = useSessionContext()
  return hasPermission(role, action, subject) ? <>{children}</> : fallback
}
// usage: <Can action="reassign" subject="lead"><ReassignButton /></Can>
