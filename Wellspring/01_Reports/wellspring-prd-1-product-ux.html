PRD Phase — Not a concept, a spec

Wellspring Operations Platform

This is Part 1 of a four-document PRD converting the approved CRM Blueprint into a build-ready specification. It assumes the Blueprint's findings (32 disconnected weekly tabs, free-text referral/insurance fields, no pipeline, no activity log) as settled context — nothing here re-argues that case. Every screen, field, rule, and permission below is written so a development team can start building without a follow-up product question.

Reading order: Part 1 (this document) — product & UX. Part 2 — automation rule catalog. Part 3 — database, API, and Google Sheets sync architecture. Part 4 — design system, security, performance, AI roadmap, sprints, testing, and acceptance criteria.

Navigation architecture

Fixed left rail, 240px expanded / 64px icon-only collapsed (state persisted per user). Sections, in order, each with role-based visibility:

Top bar

Left-to-right: sidebar collapse toggle · global search input (opens Command Palette on focus) · Quick Add button · notification bell with unread badge · task badge with due-today count · user menu (profile, theme, sign out).

Breadcrumbs

Pattern: Section › Subsection › Entity. Example: Pipeline › Table View › Lead #7786. The final segment is never a link; every prior segment is.

Quick actions, context menus, drawers, modals

Quick actions — floating action button bottom-right on Pipeline, Leads, and Tasks screens: New Lead, New Task, Log Activity.
Context menus — right-click (desktop) / long-press (touch) on a pipeline card or table row: Change Stage, Assign to…, Add Task, Flag Priority, Merge, Archive.
Right-side drawers — Lead Quick View (from Table/Kanban, no navigation away), Notification Drawer, Task Drawer. All drawers close on Escape or outside click and trap focus while open.
Modals — New Lead (short form), Confirm Merge, Bulk Reassign, Confirm Archive/Delete, Confirm Stage Automation Override. Destructive actions always require explicit confirm text, never a bare "OK."

Global command palette

⌘K/Ctrl+K anywhere in the app. Sections in result list, top to bottom: Recent (last 5 visited leads/pages) → Leads (fuzzy match on name/Client ID/phone) → Pages (all 36 routes) → Actions ("New Lead," "New Task," "Run report: Weekly Client Report"). Arrow keys navigate, Enter executes, Escape closes.

Mobile navigation

Bottom tab bar, 5 items: Dashboard, Pipeline (table view only on mobile), Tasks, Search, More (Reports/Analytics/Admin collapse here). Sidebar and top bar are replaced entirely below 768px — see Mobile Experience.

Experience · 02

Lead management

Creation

Required fields: Referral Source (channel dropdown + conditional sub-type/referrer-name), Service(s) Requested (multi-select), Zip Code (validated 5-digit, checked against active service-area list — out-of-area triggers a non-blocking warning, not a hard stop), Date of Birth (date picker; age < 18 auto-reveals Guardian Name + Guardian Phone as required). Optional at creation: Insurance Carrier (if unknown, stage cannot advance past Contacted until set — see Pipeline). Client ID is system-generated, immutable, format WS-100000 incrementing.

Editing

Inline edit on Lead Detail for all fields except Client ID and Created Date. Every field edit writes an Activity row of type field_change and an AuditLogEntry (old value, new value, editor, timestamp). Stage cannot be changed via field edit — only via the explicit Change Stage action, which runs stage-exit validation (see Pipeline).

Assignment & reassignment

New leads auto-assign round-robin across active Coordinators at that location (configurable in Settings → Pipeline Config), skipping anyone marked Out of Office. Manual reassignment (Manager/Admin only) is available from Lead Detail, Table View row action, and Kanban card context menu; reassignment writes an Activity entry and resets the "time with current owner" clock used for SLA widgets.

Status changes, notes, activity history

"Status" in the UI = pipeline stage; there is no separate free-floating status field, closing the exact ambiguity the old sheet's "Did they schedule?" column created. Notes are a dedicated Activity subtype (note), timestamped and attributable, rendered inline in the same chronological timeline as calls, emails, and stage changes — never a separate silo.

Follow-ups & scheduling

"Log Activity" captures type (Call, Email, SMS-future, In-person), outcome (Reached / No answer / Left voicemail / Bad number), and free-text note. Logging a call outcome of "Reached" surfaces a "Schedule Consultation" quick action inline. Scheduling opens a date/time/provider/location picker; on save the lead auto-advances to Consultation Scheduled and a calendar event is created.

Attachments

Drag-and-drop on Lead Detail. Accepted: PDF, PNG, JPG, DOCX, max 15MB/file. Never accepts a file typed as containing clinical notes without an explicit "This may contain PHI" acknowledgment checkbox — logged for compliance.

Duplicate handling & merge

Duplicate candidates are computed on every create/update (see automation rules AR-014–AR-017 in Part 2) using phone, email, DOB+zip, and name-similarity scoring. A match above threshold surfaces a non-blocking banner on both leads: "Possible duplicate of #7786 — Review." The Merge screen shows both records field-by-field, side by side; for each field the user picks which value survives (default: most recently updated), activity timelines are concatenated chronologically, and the losing record is soft-archived with a permanent redirect from its old ID to the surviving one.

Timeline, tags, priority

The Activity Timeline is the single source of truth for lead history — every stage change, note, call, email, task completion, and field edit appears here in one chronological stream, replacing the old sheet's single "Dates of Manual Follow Up Attempts" cell. Tags are free-form, org-scoped (e.g. adhd-waitlist, returning-patient), searchable, and multi-select. Priority is a 3-value flag (Standard / High / Urgent) settable by any staff member and required-with-reason when set to Urgent (e.g. clinical risk language detected — see AR-041 in Part 2).
