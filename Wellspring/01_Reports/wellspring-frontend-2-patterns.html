Tables

One DataTable component (components/shared/DataTable.tsx), built on TanStack Table, powers Pipeline Table View, Users, Audit Log, Webhook Deliveries, and every list screen. Screens configure it via column defs and a data source — they never reimplement sorting or pagination.

FeatureImplementation
PaginationCursor-based, matching PRD Part 3's API — DataTable exposes numbered-page UI for <1,000 rows (Users, Webhooks) and a "Load more" pattern for large sets (Pipeline Table, Audit Log)
Infinite scrollingUsed only where PRD Part 1 specifies a feed, not a table — Activity Timeline and Recent Activity widget — via useInfiniteQuery, not the DataTable component
SortingServer-side for Pipeline Table and Audit Log (sort param on the query); client-side (TanStack Table's built-in sort) for small in-memory sets like Users and Webhooks
FilteringColumn filters write to URL search params (see State Management in Part 1); the filter bar and the table read the same URL state, so a shared link reproduces the exact view
Column customizationShow/hide + reorder via a column-picker popover; persisted per-user per-table in localStorage, not the server (purely a display preference)
Bulk actionsCheckbox column enables a sticky action bar (Reassign, Archive, Export selected) that appears only when ≥1 row is selected
Row actionsKebab menu per row (desktop) / long-press context sheet (touch) — Change Stage, Assign, Add Task, Merge, Archive, mirroring PRD Part 1's context-menu spec exactly
ExportCalls the relevant PRD Part 3 export endpoint and streams the response as a Blob download — no client-side CSV/PDF generation, so exported data always matches server truth
Sticky headersposition: sticky; top: 0 on <thead> within a scroll container, so headers stay visible in dense views without JS
VirtualizationTanStack Virtual activates automatically above a 200-row threshold (Pipeline Table, Audit Log) — the component's public API is identical below and above that threshold, so no screen-level code changes when a table grows

Dashboard widgets

Every widget takes a typed config prop and renders nothing it wasn't told to — no widget fetches its own data directly; the parent dashboard page passes query results down, keeping widgets reusable across all 4 dashboard personas and the 3 domain dashboards.

Error handling

CaseHandling
Global error boundaryglobal-error.tsx — full-page fallback with "Reload" and a support-contact line; only reached if a segment-level boundary itself throws
Segment error boundaryerror.tsx per route segment — keeps the sidebar/top bar intact, only the failed content area shows the error + Retry
API failures (4xx)Inline — field-level for validation (422), a dedicated PermissionDenied component for 403, never a raw toast for something actionable in-place
API failures (5xx)Toast with Retry action; the underlying React Query mutation/query stays retryable, not discarded
Offline modeuseNetworkStatus hook (based on navigator.onLine + a lightweight heartbeat ping) drives the offline banner and disables mutation-triggering buttons rather than letting them fail loudly
Permission denied403 responses render <PermissionDenied action="..." /> — explains what was blocked, never a generic error page
Network retry UIShared <ErrorState onRetry> component used by every failed query — consistent icon, message, and button across the app
Empty statesShared <EmptyState> — icon + message + primary action ("No leads match these filters — Clear filters"), never a bare "No data"

Loading states

Every data-bearing screen gets a purpose-built skeleton matching its real layout — spinners are reserved for sub-second, non-layout-shifting waits only (button-click submits).

Screen typeLoading treatment
DashboardsSkeleton KPI row (6–8 pulsing tiles) + skeleton chart blocks; each widget's Suspense boundary resolves independently
Pipeline BoardSkeleton columns with 2–3 skeleton cards each
Pipeline Table / Audit LogSkeleton rows at the real row height (dense/comfortable) to avoid layout shift when data arrives
Lead DetailTwo-column skeleton (profile fields left, timeline entries right)
ReportsSkeleton chart + skeleton table; Report Builder's live preview shows a subtle inline spinner only (sub-second, no layout change)
Forms (submit)Button enters a loading state (spinner + disabled), form stays interactive-looking but blocked — never a full-page spinner for a form submit
Optimistic renderingStage changes, task completion, and notification read-state render instantly (see Part 1's API mapping) and roll back with a toast only on failure — the loading state most users never see

Accessibility

WCAG 2.1 AA target across the app; shadcn/ui's Radix foundation covers focus-trap, roving tabindex, and ARIA roles for dialogs/menus/tabs out of the box.
Keyboard navigation — Kanban board has a full keyboard-operable alternative (Table View plus a "Change Stage" menu), since drag-and-drop alone is never sufficient.
Focus management — modals/drawers trap focus and return it to the trigger element on close; route changes move focus to the new page's <h1>.
Screen reader support — toasts and notification updates use aria-live="polite"; table headers use proper scope; status pills pair color with visually-hidden text (e.g. "Eligible").
Color contrast — verified ≥4.5:1 for body text in both themes against the PRD Part 4 palette; semantic colors never used as the sole signal.
ARIA attributes — aria-current="page" on active nav items, aria-expanded on accordions/dropdowns, aria-busy during data loads, aria-describedby linking every form error to its field.
