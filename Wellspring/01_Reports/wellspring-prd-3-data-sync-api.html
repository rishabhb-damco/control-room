Schema (PostgreSQL DDL)

Representative core tables — full DDL for all 21 tables follows the same conventions: uuid primary keys via gen_random_uuid(), org_id on every row for tenant isolation, created_at/updated_at with trigger-maintained updated_at.

-- core lead record: thin on identity, joins out to the clinical system of record
CREATE TABLE leads (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id              uuid NOT NULL REFERENCES organizations(id),
  display_id          text NOT NULL UNIQUE,          -- WS-100032, generated
  client_ref          text,                                -- FK into external EHR, nullable
  stage_id            uuid NOT NULL REFERENCES pipeline_stages(id),
  priority            text NOT NULL DEFAULT 'standard'
                        CHECK (priority IN ('standard','high','urgent')),
  priority_reason     text,
  owner_id            uuid REFERENCES users(id),
  location_id         uuid NOT NULL REFERENCES locations(id),
  provider_id         uuid REFERENCES providers(id),
  referral_source_id  uuid NOT NULL REFERENCES referral_sources(id),
  referrer_name       text,
  insurance_carrier_id uuid REFERENCES insurance_carriers(id),
  dob                 date,
  is_minor            boolean GENERATED ALWAYS AS (
                        dob IS NOT NULL AND dob > (now() - INTERVAL '18 years')
                      ) STORED,
  guardian_name       text,
  guardian_phone      text,
  zip                 text,
  sex                 text,
  services            text[] NOT NULL DEFAULT '{}',
  appointment_type    text,
  tags                text[] NOT NULL DEFAULT '{}',
  lost_reason         text,
  lost_at             timestamptz,
  reactivated_from_id uuid REFERENCES leads(id),
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now()
);

-- append-only interaction log — replaces the sheet's single free-text follow-up cell
CREATE TABLE activities (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  lead_id       uuid NOT NULL REFERENCES leads(id) ON DELETE CASCADE,
  type          text NOT NULL CHECK (type IN
                  ('note','call','email','stage_change','field_change','attachment','merge')),
  outcome       text,
  body          text,
  staff_id      uuid REFERENCES users(id),
  occurred_at   timestamptz NOT NULL DEFAULT now(),
  source        text NOT NULL DEFAULT 'manual' CHECK (source IN ('manual','automation','sheet_sync'))
);

CREATE TABLE tasks (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  lead_id         uuid REFERENCES leads(id) ON DELETE CASCADE,
  type            text NOT NULL CHECK (type IN ('follow_up','reminder','ops','escalation')),
  title           text NOT NULL,
  due_at          timestamptz NOT NULL,
  assigned_to     uuid NOT NULL REFERENCES users(id),
  status          text NOT NULL DEFAULT 'open' CHECK (status IN ('open','completed','overdue')),
  completed_at    timestamptz,
  outcome_note    text,
  source          text NOT NULL DEFAULT 'manual',
  rule_id         text REFERENCES automation_rules(id)
);

CREATE TABLE sync_state (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id          uuid NOT NULL REFERENCES organizations(id),
  sheet_id        text NOT NULL,
  sheet_tab       text NOT NULL,
  row_number      int NOT NULL,
  lead_id         uuid REFERENCES leads(id),
  row_hash        text NOT NULL,
  last_synced_at  timestamptz,
  status          text NOT NULL DEFAULT 'pending' CHECK (status IN ('synced','pending','conflict','error')),
  UNIQUE (sheet_id, sheet_tab, row_number)
);

CREATE TABLE sync_conflicts (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  sync_state_id   uuid NOT NULL REFERENCES sync_state(id) ON DELETE CASCADE,
  field           text NOT NULL,
  sheet_value     jsonb,
  crm_value       jsonb,
  detected_at     timestamptz NOT NULL DEFAULT now(),
  resolved        boolean NOT NULL DEFAULT false,
  resolution      text CHECK (resolution IN ('keep_sheet','keep_crm','manual'))
);

CREATE TABLE audit_log_entries (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id        uuid NOT NULL REFERENCES organizations(id),
  entity_type   text NOT NULL,
  entity_id     uuid NOT NULL,
  field         text,
  old_value     jsonb,
  new_value     jsonb,
  user_id       uuid REFERENCES users(id),   -- null = system/automation
  rule_id       text,
  at            timestamptz NOT NULL DEFAULT now()
);

Fast pipeline board queriesINDEX ON leads (org_id, stage_id, location_id)

Audit trail is immutableNo UPDATE/DELETE grants on audit_log_entries at the DB role level — insert-only
Guardian fields required for minorsApplication-layer validation at save time (AR-040); DB permits null so historical/legacy rows aren't blocked on backfill

Future scalability considerations

Partitioning — activities and audit_log_entries partition by month once volume passes ~5M rows; both are append-mostly and query patterns are date-bounded.
Read replicas — dashboard/report queries route to a read replica once concurrent staff exceed ~50, keeping the primary free for the write-heavy pipeline board.
Multi-location/multi-tenant — the org_id-on-every-row + RLS pattern means onboarding a second Wellspring-like client is a data-isolation non-event, not a schema change.
Search — Postgres full-text to start; if lead volume or query complexity grows, the search layer sits behind an interface so it can move to a dedicated index (e.g. Meilisearch) without touching callers.

PRD Part 3 of 4 · Google Sheets Sync

Two-way synchronization architecture

Non-negotiable per the brief: the sheet stays the primary data source in Phase 1. The design below treats the sheet as just another repository implementation behind the same interface the database will use later — so replacing it is a swap, not a rebuild.

Known constraint: the Sheets API enforces 60 reads/min and 60 writes/min per connected account (confirmed in the live integration). Every component below is designed around that ceiling — batched reads, queued writes, and hash-based change detection so unchanged rows never consume a read/write cycle.

Every new row without a value in the hidden CRM Lead ID column is treated as a create; every row with an ID and a changed hash is treated as an update. Unchanged rows (identical hash) are skipped — this is what keeps a full-tab weekly re-fetch inside the API rate limit.

Writing only the changed cell range (not the full row) minimizes the surface a concurrent human sheet-edit can collide with, and keeps each write inside the 60/min budget even during a burst of CRM activity.

Conflict resolution

A conflict exists only when the same field changed in both places since the last successful sync — everything else merges automatically, field by field.

ScenarioResolution
Field changed in Sheet onlyAuto-apply to CRM
Field changed in CRM onlyAuto-apply to Sheet
Different fields changed in each, same rowAuto-merge both changes — no conflict
Same field changed in both since last syncCreate sync_conflicts row (AR-052); surface in Sync Monitor; Admin picks Keep Sheet / Keep CRM / Manual entry
Row deleted in Sheet, lead has activity in CRMNever auto-delete a lead with history — flag for Admin review instead

Permanent Lead ID: assigned at first creation (whichever side creates it first) and never regenerated — the hidden sheet column and the CRM display_id are the same value for the life of the record, including through a merge (the surviving ID wins; the archived one becomes a redirect, not a deletion).

Offline queue

Mobile/PWA clients write local edits to an IndexedDB-backed outbox when offline. On reconnect, the outbox replays through the identical CRM→Sheet write path and conflict-detection logic above — offline is not a special case, it's a delayed enqueue. Each queued item carries a client-generated idempotency key so a retried replay after a partial failure never double-applies.

Sync failure logging & recovery

Every sync job attempt (in either direction) writes a row to a sync_job_log table: job type, target row, attempt number, result, error detail. Exponential backoff (2s, 8s, 32s) on transient errors (429/500); after 3 consecutive failures on the same row, that row's status flips to error, the org-wide sync pauses (not just that row) and AR-053 alerts the Admin — failures are visible and recoverable from the Sync Monitor screen, never silent.

Future database cutover — designed in from day one

Application codecalls LeadRepository interface only
→

The application never queries "the sheet" or "the database" directly — it calls LeadRepository.find(), .save(), .search(). Cutover is: (1) run a one-time migration that walks every sync_state row and inserts the corresponding data into the leads table, preserving display_id; (2) flip a config flag from SheetRepository to SqlRepository; (3) keep the Sheets connector alive in read-only "mirror" mode for one billing cycle as a safety net, then retire it. No screen, API endpoint, or automation rule changes.
